# Low-Level Design

## 1. Purpose

A concrete implementation design for the Python graph model and interactive PySide6 workbench. It deliberately starts with a small working graph editor and evolves toward a self-describing semantic modelling system. All interfaces below are **proposed**, not implemented.

## 2. Kernel: smallest useful model

### 2.1 Records

| Record | Required fields | Notes |
| --- | --- | --- |
| Node | id, label, properties | id is immutable; label is editable |
| Connection | id, source_id, target_id, predicate_id, properties | Directed, first-class identity |
| Graph | id, label, properties | Named membership scope |
| GraphMember | graph_id, element_id | Membership is not ownership |
| ChangeSet | revision, command_id, affected_ids, change_kind | Published after commit |
| ViewDefinition | id, representation_id, graph_id, filters, layout, interaction | References canonical IDs |
| PresentationState | view_id, element_id, x, y, dimensions | Separate from semantics |

IDs are opaque strings generated by the application (UUIDs are sufficient). Human names are never identifiers. Store structured property values as JSON-compatible data, with schema validation at the application boundary.

For MVP, a connection is binary but carries its own ID. Later generalize to Relation(id, predicate_id, bindings[role_id, participant_id]) without changing canonical object identity.

### 2.2 Kernel operations

~~~text
create_node(label, properties?) -> NodeId
update_node(node_id, patch) -> ChangeSet
delete_node(node_id, policy=RESTRICT) -> ChangeSet
create_connection(source_id, target_id, predicate_id) -> ConnectionId
delete_connection(connection_id) -> ChangeSet
create_graph(label) -> GraphId
add_member(graph_id, element_id) -> ChangeSet
remove_member(graph_id, element_id) -> ChangeSet
get_node(node_id) -> Node
get_connections(node_id?, predicate_id?) -> Sequence[Connection]
get_members(graph_id) -> Sequence[ElementId]
~~~

These are conceptual signatures; mutating operations are exposed through the ModelController, which owns transactions and authorization. The low-level repository is not called directly from the GUI.

### 2.3 Kernel invariants

- Every canonical object has a unique stable ID.
- A connection references existing endpoints and a resolvable predicate ID (or an explicitly marked unresolved definition during later import workflows).
- Graph membership references existing objects.
- No partial updates are observable after a failed command.
- Deletion defaults to RESTRICT when referenced; cascade requires an explicit command/policy.
- Duplicate membership is idempotent or rejected consistently (choose one and test it).
- Membership does not imply a semantic contains relation.
- A relation is an object, so it can later be referenced by annotations or evidence.

## 3. Semantics and self-description

### 3.1 Start simple

At first, the application recognizes a small set of built-in predicate IDs such as contains and depends_on. These are bootstrap data, not domain-specific Python classes.

### 3.2 Make definitions graph objects

After the editor works, create a trusted semantic vocabulary graph containing Type, Predicate, instance_of and subtype_of. User-defined Component, Interface, Sensor and requires are ordinary nodes classified through instance_of.

~~~text
core:Type --instance_of--> core:Type
core:Predicate --instance_of--> core:Type
domain:Sensor --instance_of--> core:Type
domain:Sensor --subtype_of--> domain:Component
model:SensorA --instance_of--> domain:Sensor
~~~

The self-reference of core:Type is an explicit bootstrap exception. It is **not** permission for arbitrary recursive definitions.

### 3.3 Semantic resolver contract

~~~text
resolve_type(element_id, context) -> ResolvedType | Unresolved
is_subtype(candidate_type, expected_type, context) -> bool | Unresolved
resolve_predicate(predicate_id, context) -> PredicateDefinition | Unresolved
validate_connection(connection, context) -> Sequence[Diagnostic]
~~~

Use graph-stored definitions for interpretation. Unknown semantics return Unresolved, not false. Prevent unbounded subtype cycles with visited sets and deterministic diagnostics.

### 3.4 Later semantics

Add role/domain/range constraints, scopes/imports, evidence, inference and typed expression trees. Do not execute arbitrary Python from graph data. Evaluator-specific inference remains in the evaluator boundary.

## 4. Model controller and transactions

### 4.1 Command contract

~~~text
ModelCommand:
  command_id: string
  kind: CreateNode | UpdateNode | DeleteNode | CreateConnection | ...
  expected_revision: integer | null
  payload: validated typed data
  origin: ui | import | llm | automation
~~~

The controller validates commands, applies them within one repository transaction, increments model revision and publishes a ChangeSet only after commit. A stale expected_revision returns Conflict without mutating state.

For MVP, use a single serialized writer. Emit events on the GUI thread (or marshal them to it) before updating Qt scene items. Keep callbacks out of database transactions.

### 4.2 Undo/redo

Capture inverse operations or a before/after patch with each committed user command. Undo/redo are new controlled transactions and must obey reference integrity. Qt's QUndoStack can be an adapter; core undo semantics must not depend on Qt.

### 4.3 Candidate proposals

An LLM or user preview creates a CandidateChangeSet, not a committed ChangeSet. Candidate operations are validated against a model revision; preview is a temporary overlay. Approval requires an explicit UI-mediated action and revalidation against the current revision before commit.

## 5. SQLite persistence

### 5.1 Proposed logical schema

| Table | Key fields | Notes |
| --- | --- | --- |
| nodes | id PK, label, properties_json | Canonical objects |
| connections | id PK, source_id FK, target_id FK, predicate_id, properties_json | Foreign keys enforced |
| graphs | id PK, label, properties_json | Graph identity |
| graph_members | graph_id FK, element_id, PK(graph_id, element_id) | Element ID validation via repository; mixed-type IDs require a shared element registry or explicit enforcement |
| revisions | revision PK, command_id, timestamp, change_json | Audit and synchronization |
| view_definitions | id PK, representation_id, graph_id, config_json | Saved projections |
| view_positions | view_id, element_id, x, y, width, height | Presentation only |
| workspaces | id PK, split_tree_json | Saved pane arrangements |
| schema_meta | key PK, value | Schema version |

**Implementation detail:** SQLite foreign keys cannot reference a polymorphic union of multiple tables. Either use a shared elements(id, kind) registry from day one or enforce graph_members.element_id against a unified repository abstraction with explicit tests. Prefer the shared elements registry if mixed node/connection/graph membership is required in MVP.

### 5.2 Save semantics

- Use PRAGMA foreign_keys=ON on every connection.
- Commit semantic commands atomically.
- Store view position changes independently of semantic revisions.
- Store schema_version and implement migrations.
- Verify round-trip of IDs, relationships, graph membership, view positions and pane layout.

## 6. Projection engine

### 6.1 View contract

~~~text
ViewDefinition:
  id: view-001
  representation_id: structural
  source_graph_id: graph-computer
  root_id: null
  filters: {predicates: [contains], depth: 3}
  overlays: []
  layout_id: manual

DiagramModel:
  nodes: [DiagramNode(diagram_id, semantic_id, label, style_key)]
  edges: [DiagramEdge(diagram_id, semantic_id, source_diagram_id, target_diagram_id)]
  revision: 12
~~~

Projection output is derived and disposable. Keep a semantic_id mapping on each diagram item. A projected/derived edge that has no canonical relationship ID must carry derivation provenance and an explicit read-only policy.

### 6.2 Representation registry

~~~text
RepresentationProvider:
  id
  supported_entity_types
  supported_predicates
  project(model_snapshot, view_definition) -> DiagramModel
  permitted_edit_commands
~~~

MVP providers: structural, dependency, semantic. Later plugins may define UML, C4, SysML-inspired, capability and state-machine projections. Visual resemblance is not proof of standards conformance.

### 6.3 Incremental refresh

MVP: rebuild affected panes on each committed ChangeSet. Later: index dependencies from semantic IDs to view IDs and update only changed diagram elements. Layout-only changes must not invoke model evaluation.

## 7. Qt canvas

### 7.1 Components

| Class | Responsibility |
| --- | --- |
| MainWindow(QMainWindow) | Application shell, menus, docks |
| CanvasView(QGraphicsView) | Pan, zoom, viewport |
| CanvasScene(QGraphicsScene) | Diagram item lifecycle |
| NodeItem(QGraphicsItem) | Render node, selection, drag |
| EdgeItem(QGraphicsItem) | Render relationship and endpoints |
| CanvasController | Translate UI gestures into commands |
| PropertiesPanel | Edit selected canonical object |
| ModelExplorer(QTreeView) | Hierarchy/graph navigation |

The CanvasController sends model commands. Node dragging updates per-view PresentationState only. Do not store QGraphicsItem pointers in canonical model records.

### 7.2 Workspace layout

Represent workspace as Split(axis, ratio, first, second) or Pane(view_id, tabs). Render via nested QSplitter and QTabWidget. Each pane chooses a representation, graph scope and independent filters. Selection linking is opt-in; synchronize by semantic ID.

### 7.3 Performance and thread safety

Start with simple full-pane redraw for small graphs. For large models, add viewport culling, layout workers and change-driven deltas. Only touch QGraphicsScene/QGraphicsItem on the Qt GUI thread.

## 8. LLM/MCP adapter (later milestone)

### 8.1 Proposed tools

| Tool | Access | Result |
| --- | --- | --- |
| model.list | Read | Scoped list of entities |
| model.inspect | Read | Definitions and relationships |
| model.search | Read | Matching canonical IDs |
| model.propose | Candidate write | Proposed commands, not committed |
| model.validate_proposal | Read/validate | Diagnostics |
| model.preview | Read | Candidate diagram diff |
| model.request_approval | Approval workflow | Approval request; no implicit commit |

Actual commit is a trusted application action after explicit approval, revision check and validation. Do not expose an unguarded direct-write tool to an LLM.

### 8.2 Context and trust

Supply selected IDs, scoped neighborhood, relevant definitions, model revision and representation profile. Do not rely on screenshots as canonical context. Limit read scope; validate tool arguments; reject arbitrary code execution and prompt-injected instructions from imported model text.

## 9. Evaluator integration

Define an EvaluationAdapter that sends a versioned model snapshot and policy to the parent evaluator, then receives diagnostics with source model IDs and evidence. Do not assume the existing evaluator implements all workbench semantics. Mark unsupported evaluations unresolved and display them separately from invalid findings.

## 10. Error taxonomy

| Code | Condition |
| --- | --- |
| SD-ID-001 | Duplicate identity |
| SD-REF-001 | Missing referenced object |
| SD-REL-001 | Invalid connection structure |
| SD-SEM-001 | Unknown semantic definition |
| SD-SEM-002 | Semantic constraint violation |
| SD-TXN-001 | Stale revision / conflict |
| SD-STORE-001 | Persistence or migration failure |
| SD-VIEW-001 | Unsupported representation or projection |
| SD-LLM-001 | Unapproved or invalid proposal |

All diagnostics include code, message, affected IDs and relevant revision; add source/provenance when available.

## 11. Design constraints and tradeoffs

- Prefer simple Python dataclasses for internal records; use Pydantic for untrusted inputs and serialization boundaries.
- Do not make NetworkX authoritative; build NetworkX projections only for algorithms.
- Prefer Qt Graphics View for the first desktop prototype; reconsider GLSP or Qt Quick only if editing complexity/performance demands it.
- Start with manually positioned nodes and a simple layout; Graphviz/ELK integration is optional later.
- Do not confuse model type hierarchy, abstraction hierarchy (L0–L5), and UI diagram hierarchy.
- Define a finite trusted semantic bootstrap; self-description does not eliminate the need for interpreter code.
